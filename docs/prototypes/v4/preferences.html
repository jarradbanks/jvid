Preferences and Themes

Mockups for #257 (Preferences: sections, and dropdowns that fit) and #258 (a Theme picker in Preferences). Every dialog sits over the editor at its minimum window size, 960×600. The fields are the real ones from preferences.rs; the palettes are the built-ins from themes.rs.

Picking a theme in any alternative applies it to the whole mock editor at once, the way it will in the app. Neon is a broken file, so you can see the error and the fall back to Dark.

What's Wrong Now

  • The list grows to its widest device name, so it runs past the dialog's edge and covers Done (dashed). The popup that opens is wider than the window at 960×600 on some laptops.
  • A 360px box with two unlabelled rows in a grid. Nothing groups Language apart from Input Device, and the one help line sits under both fields, in 10px type, explaining only the first.
  • Three built-in themes and live-reloading TOML themes exist in themes.rs, but the only way to switch is to edit settings.toml by hand.
  • A theme file that fails to parse returns Theme {path}: {error} with nowhere next to the choice to show it.
  • A save error lands at the bottom of the dialog, not under the field that failed.

Alternatives

Three dialog structures, each paired with one way of picking a theme: A sidebar with swatch cards, B one scrolling page with a dropdown and a token strip, C header tabs with a list of live previews. The pairings can be swapped; each picker works in each dialog.

States

Drawn in B, the recommended structure. The dropdown rules are the suite-ui change in #257, so every dropdown in the app gets them.

Input Device Open at 960×600, With a Very Long Name

  • The list stays inside the dialog body. It opens on the side with more room (here, above, because Input Device is the last field) and stops 8px short of the body's edge. Past that it scrolls. Done is never covered.
  • The list is as wide as its field. Long names end in an ellipsis; hovering one shows the full name in a tooltip after 500ms, and so does hovering the closed field.
  • The chosen device keeps its row when it's unplugged, as input_rows() does now, with a Not Connected tag so the choice doesn't look broken.
  • Fifteen devices is a normal streamer's machine: virtual cables, NVIDIA Broadcast, Steam and a capture card each add one.

Broken Theme File

  • The dropdown keeps the file's name with a Red border, so you can see what you picked. The error sits directly under it, in the theme.error string: Theme {path}: {error}.
  • TOML's multi-line error is folded to one line: line, column, and the theme.bad_color message.
  • The editor falls back to Dark, and a second line says so. LiveTheme already re-reads the file when it changes, so fixing it in a text editor clears the error without reopening Preferences.
  • In the list it shows a Red alert where its colours would be, and Can't Load. It stays pickable, so you can see the error again.

Light and High Contrast

Bundled Themes

  • Dark (default), Light and High Contrast stay compiled in, as BUILT_IN has them, so the app always has a theme that loads.
  • Warm Dark and Soft Light ship as warm-dark.toml and soft-light.toml, copied into the themes folder on first run, so they double as commented templates for custom themes. Warm Dark only warms the neutrals a few degrees; the accent stays blue, so it can't drift back to the rejected warm-grey-and-amber look. It's opt-in, never the default.
  • A folder theme is listed under its file name in Title Case (nord-night.toml is Nord Night). The theme setting keeps saving the built-in name or the file's path, as LiveTheme::new reads it.

Recommendation

B: one scrolling page, with the Theme dropdown and token strip. There are three settings. A sidebar or tabs would put two of them behind a click to save space nobody needs; B shows all three at 960×600 without scrolling, each with its help under the field it explains. The dropdown copes with any number of folder themes, and the palette chip on each row previews it before you pick. Picking applies to the whole editor at once, which is a bigger preview than any thumbnail.

B's section heads map one-to-one onto A's sidebar. When Preferences grows past a screenful (Playback, Keyboard Shortcuts), move to A without reworking the sections. Keep C's broken-file row (Red alert, Can't Load) in the dropdown, as drawn here.

Build order: the suite-ui dropdown cap first (side with more room, capped to the dialog body, field-width, ellipsis, tooltip), since every dropdown in the app needs it, then the dialog.
